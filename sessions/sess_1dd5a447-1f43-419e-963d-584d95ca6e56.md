## 这套工作流是干嘛的

视频里的三步：Stitch 出高保真页面 → Codex 从页面反推 PRD → 人审 PRD 后再让 AI 反改页面，最后**“拿去和用户做需求确认”**。它的核心价值是“乙方替客户做系统前的需求对齐”——通过原型和 PRD 互相校验，减少和客户来回扯皮。视频里的例子（报表系统、员工处理入口、配置员角色）也印证了这是 B 端外包场景。

## 为什么主体不适合你

- 你是独立开发者，**自己就是需求方**，没有“和客户确认 PRD”这一环。引入 PRD 流程对 vibe coding 是纯负担。
- 你已有的更轻的解法覆盖了它的痛点：视频说“过几天回来不记得设计决策”，你的 memory 和 handoff 机制就是干这个的，不用上 13 章的 PRD。

## 值得拿走的两个点

1. **提示词里必须写“核心痛点”**，不只写功能。原话的意思是：只写功能，AI 会做成一个平庸页面；写清痛点，它才知道优先解决什么。这个技巧是通用的——你给我写需求时同样适用。
2. **Stitch 本身可以一用**：Google Labs 的免费 AI 设计工具（每月 350 次生成），文字描述直接出高保真页面 + HTML/CSS/Tailwind 代码，适合你多项目并行时快速看一个新点子“长什么样”。它走 MCP 协议（视频里说的“CP 功能”就是 MCP 的转写错误，“流式 TP”是流式 HTTP 传输），**接法在 ZCode 里同样适用**，不用换成 Codex——Stitch 生成的连接地址和密钥配到我这边的 MCP 配置里就行，之后可以直接在对话里让我读它的设计稿写代码。
