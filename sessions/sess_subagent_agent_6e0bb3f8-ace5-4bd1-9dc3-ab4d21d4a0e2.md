### 决策1：流程结构主干 → 选 A 的 4 幕分块，但修补 A 的分组漏洞

**裁决**：采用 4 幕分块结构（A 的主干），每幕对应一个维度模型组（S/F/B/W），各 6 题。

**理由（引用来源）**：
- A 和 C **独立收敛到"4 幕"**——这是弱证据指向该结构正确（不是偶然一致）。但我要标注：两案都选 4 幕可能部分源于"4 个维度模型组"这个**数据结构既成事实**的共同偏见，而非独立的需求论证。不过 config.ts 确实定义了 S/F/B/W 四个 model 组（已验证），所以这个收敛有客观基础。
- 否决 B 的探测轮+自适应排序：理由见决策5，且 B 的"前12题固定覆盖全维度"恰好是**当前正向12题既成结构**，B 把它当创新实则是现状。
- 否决"不重排只加幕标签"（A 的 fallback）：契约 A5 明确要"流程重构"，纯加标签不达激进程度门槛。

**关键修补（A 的盲点）**：A 声称"meta 已按模型分组，分幕只是显性化"——**经验证不成立**。数据库实际题序是 S1,F1,B1,W1,S2,F2... 的**轮转混排**，不是按模型聚类的。要实现 A 的分幕**必须重排题序**（改 DB 的 order 字段或前端 RenderQueue 重排）。这是 A 低估的实现成本，已在共同盲点#1 标注。

### 决策2：幕间反馈机制 → 选 C 的氛围词揭示为主，融合 A 的提问式

**裁决**：幕间过渡层采用 **C 的"因子共鸣"渐进式维度氛围词揭示** 为主体（输出已答维度的氛围词如"侵蚀加深""羁绊觉醒中"，**绝不输出角色/百分比**），叠加 **A 的"提问式"审判官批注**作为收尾。

**理由**：
- 这是最能制造"自我投射感"（契约 R6）的组合。C 的洞察——**"让用户在答题中持续获得关于自己的洞察，而非等到结果页"**——是对"第10题厌烦"最精准的杠杆：它把"忍受过程"转成"主动想看下一题揭示"。A 的分块完成感是"我快做完了"的减负感，C 的揭示是"我想知道我是什么"的获得感——后者更强。
- C 的"氛围词而非角色/百分比"是关键的安全约束，守住"结果页惊喜"不剧透，且与 match 算法解耦。A 的批注是"提问式叙事"，缺少自我揭示的获得感。
- B 的计分直问是测量手段不是反馈手段，性质不同，不在此决策内。
- **诚实标注**：C 文档截断，"渐进式自我揭示"的具体算法（ResonanceEngine 如何从 dimScores 映射氛围词）未提供。实现者需自行设计映射表——但这是确定的、低风险的设计任务，不影响方向选择。

### 决策3：第二人称选项格式 → 选 A 的括号内心独白

**裁决**：采用 A 的格式——**括号包裹的内心独白**，主语统一"你"，去掉祈使动作动词，保留感受判断，分数不动。

**理由**：
- **契约 R4 是硬约束**："如果方案涉及减题或改题型，则系统应当保证 12 维度仍各有有效测量覆盖，且任意两常规角色向量至少差 3 个维度。" B 的替换反向题会**改题型**，必须重新验证 R4。经验证当前反向题分布：S1,F1,B1,W1,S2（题13-17）+ F2,B2,W2,S3,F3,B3,W3（题20-26）= 12 维度全覆盖。B 要删的"低区分反向题"需先证明低区分，但**没有任何方案提供区分度数据**——这是共同盲点#4。在无数据支撑下替换，风险不可控。
- B 的"直问分×0.5归一化"是精巧设计，但引入新的计分逻辑改动（answer-processor.ts），且归一化后维度总分区间 2-6 的保持需逐维度校验——增加 R4 违反面。
- A 的"不计分纯叙事"零算法风险，直问只作情绪调剂，不影响 match。这最稳。
- 直问位置：3 个节点位于幕 I→II、II→III、III→IV 之间（与决策2的氛围词揭示共用过渡层）。

---

### 决策5：题序重排策略 → 选 A 的确定性重排，否决 B 的动态重排

**裁决**：**确定性重排**（按维度模型 S→F→B→W 分幕，幕内正向/反向题打散避免相邻暴露），否决 B 的按 clarity 动态重排。

**理由**：
- B 的动态重排有三个问题：(1) **localStorage 恢复复杂度**（需存 adaptiveOrder，B 自己承认）；(2) **A/B 测试不可复现**——同一用户两次测试题序不同，无法归因效果差异（共同盲点#5）；(3) **门控/触发语义锚点破坏**（B 自己标为最高风险，且承认"无法完全消除"）。一个自己承认最高风险无法消除的方案，不应作为主干。
- A 的确定性重排：可复现、可测试、localStorage 零改动（只存 currentIndex）。代价是失去"模糊维度前置深挖"的自适应收益——但该收益缺乏数据支撑，且契约 R8（自适应）标注为"可选/衍生"，非必须。
- **重排的 R4 校验**：重排只改 order 不改 dim/score，match 通过 optionId 反查（已验证 match.ts），与顺序无关。R4 维度覆盖不变。安全。

### 决策6：门控/触发题位置 → 保留原位，否决所有方案的挪动

**裁决**：**门控题（当前题18）和触发题（当前题19）保留在原数组位置附近**，作为分幕结构中的"最终审判"节点，不挪动到绝对位 25/26（B）或 Act IV 末尾（A）。

**理由（基于实现验证的决定性裁决）**：
- 经数据库验证，当前门控在题18、触发在题19，**插在反向5题和反向7题之间**。这是既成事实。
- A 提议挪到 Act IV 第7-8题（约题23-24），B 提议绝对位 25/26。两者都**挪动了门控位**。
- **挪动门控有真实风险**：门控的 `gateValue` 触发 `applyGateBonus`（match.ts 第116-129行），给特定维度加分（如 destroy 给 S 维度加成）。门控位影响"用户在什么疲劳度下做这个关键决策"——挪到更靠后（题25）用户更疲劳，可能影响 destroy/endure 选择分布，进而影响特殊角色（YUKI/ETL）触发率。**没有任何方案分析过这个连锁影响**（共同盲点）。
- 保留原位（题18/19附近）：最小改动，门控语义不变，分幕时把门控/触发作为"幕间或幕末的最终审判"叙事节点，自然融入。
- 触发题条件渲染（`gateValue==="destroy"||"endure"`，TestScreen 第106/129行）完全保留。

## 3. 共同盲点（最高价值产出）

### 盲点#1（致命）：三方案都误判了数据源——题目来自数据库，不是 quiz-content.ts

**缺口**：A、B、C 都把 `quiz-content.ts` 当作改造对象（A 明写"改动文件：仅 quiz-content.ts"；B 写"改动 quiz-content.ts"）。但 `/api/quiz/route.ts` 第17-20行显示运行时题目来自 `db.question.findMany()`，quiz-content.ts 的 QUESTIONS 只是 **seed 数据**（prisma/seed.ts 用它灌库）。dev.db 实际题序经我查询确认与 quiz-content.ts 一致，但**改 seed 文件不会自动同步到已部署的数据库**——需要写迁移脚本或重新 seed。

**为什么重要**：这直接影响所有方案的实现切片。方案 A 的 S1 切片"改 quiz-content.ts 的 options[].label + i18n"实际上要改成"改 DB 的 Question.translations + Option.label，并通过 admin API 或迁移脚本推送"。第二人称改造、分幕重排、直问插入全部是 DB 层操作。低估这个会让工期估算偏离。

**建议处理**：最终 ADR 必须明确数据层改造路径——是改 seed 重新灌库（开发期），还是通过现有 admin API（`/api/admin/questions/[id]`）逐条更新（生产期），还是写 Prisma 迁移。**这是开放问题，需人确认部署流程。**

---

### 盲点#2（高）：三方案都没验证"4幕与既成题序的冲突"

**缺口**：A 声称"meta 已按模型分组，分幕是显性化"——经验证**错误**。当前题序是 S1,F1,B1,W1 轮转混排（非按模型聚类）。C 的"戏剧分4幕"也隐含重排但未说明。三方案都没意识到：**要实现分幕必须重排题序，而重排是改 DB 的 order 字段（或前端 RenderQueue 重排）**，不是"显性化已有结构"。

**为什么重要**：A 把这当成"零结构改动"低估了风险。重排题序会改变用户记忆中"上一题是审判题，这题还是审判题"的预期，可能引发"题目重复感"——这正是 A 自己标的风险#1（同维度正反两题相邻暴露）。但 A 以为靠"幕内分两场"能缓解，没意识到**分幕本身就强制了同维度聚类**。

**建议处理**：分幕内必须严格打散正向/反向题顺序（如 Act I 的 6 题不能是 S1+,S1-,S2+,S2-,S3+,S3-，必须 S1+,S2+,S3+,S1-,S2-,S3- 并间隔≥2题）。这是硬实现约束，写进 ADR。

---

### 盲点#3（高）：三方案系统性低估 i18n 改造成本

**缺口**：系统支持 **4 种语言（zh-CN, zh-TW, en, ja）**（i18n.tsx 第5行）。三方案都聚焦中文示例，对其他 3 语言只字未提改造量。改造涉及：(1) 所有 26 题 × 3 选项 = 78 条 option label 改第二人称内心独白，×4 语言 = **312 条文案重写**；(2) 4 个幕标题 + 幕间旁白，×4 语言；(3) 3 个直问题 + 选项，×4 语言；(4) 氛围词映射表，×4 语言。**没有任何方案估算过这个工作量**。

**为什么重要**：第二人称内心独白不是机械翻译——英文/日文里"你"的内心独白语气、括号/引号符号、敬语层级都需要本地化创作。这是**内容创作工作量，不是工程工作量**，可能成为整个项目的关键路径瓶颈。C 的"氛围词揭示"还额外增加 ResonanceEngine 的多语言氛围词词库——每语言需独立设计氛围词的叙事调性。

**建议处理**：ADR 必须把"4 语言内容重写"列为独立工作流，与工程切片解耦。可能需分语言灰度（先 zh-CN 上线验证，再补其他语言）。**这是开放问题，需人确认是否所有语言同步上线。**

---

### 盲点#4（中高）：三方案对"感知提速"都没有可证伪的 A/B 验证设计

**缺口**：契约 R5/R7 是主观指标（"投入度""进展可感"），三方案的提速声称（A: -15-25%感知时长；B: -13%实际时长；C: 心流）**全部无法直接测量**。A 提了"GA 监测跳过率>40%则缩短"作为单一信号，B 提了"Top1 分布相关性>0.9"作为信度校验——但**没有任何方案设计能证伪"流程改造有效"的实验**。

**为什么重要**：如果上线后无法判断"改造是否真的缓解了第10题厌烦"，整个项目就是不可证伪的赌博。"感知时长"无法直接测，只能用代理指标（完成率、放弃率、中段停留时长、单题响应时长）。但代理指标的解释有歧义——比如 B 的 confirm 型轻题缩短单题时长，可能被误读为"提速成功"实则是"用户没认真读"。

**建议处理**：ADR 必须包含 A/B 实验设计——feature flag 切流，对照组=当前线性流程，实验组=分幕流程，关键指标：(1) 整体完成率（ abandonment 在题10/18/26 三个点）；(2) 单题中位响应时长（分幕前后段对比）；(3) 结果页分享率（投射感的下游信号）。**预设显著性阈值，达不到就回退。**

---

### 盲点#5（中）：三方案的降级/fallback 都不彻底

**缺口**：A 的 fallback 是"退回纯幕标签方案"，B 的退路是"直问不计分仅作叙事调剂"，C 提"降级开关"——但**没有方案设计完整的 feature flag 回退路径**。具体：(1) DB 的 order 字段一旦重排，回退需反向迁移；(2) option label 一旦改成第二人称，回退需备份原文案；(3) 幕间过渡组件一旦上线，回退需 flag 控制渲染。

**为什么重要**：契约锁定的是"动效时序不动"和"算法不动"，但**内容改造（第二人称、分幕、直问）是可逆性最差的部分**。如果改造效果不好（见盲点#4 无法证伪风险），能否干净回退决定了项目风险上限。

**建议处理**：ADR 强制要求——所有内容改动在 DB 层保留 `original_label`/`original_order` 字段或独立备份表；流程结构用 `feature_flag` 控制（`flow_structure: "linear" | "acts"`），前端根据 flag 选择 RenderQueue 策略；分幕重排在前端 RenderQueue 层做（不改 DB order），这样回退只需翻 flag。

## 4. 最终融合 ADR（给实现者的指令）

### 背景
魔女审判人格测试当前是 26 题线性流程（12正向+5反向+门控+触发+7反向），用户在第10题前后出现投入度下降。契约要求在**不动700ms单题时序、不减题不降信度、不改匹配算法**的前提下，通过流程结构重构 + 内容三层改造（选项第二人称化 + 直问 + 分幕）实现感知提速与自我投射感增强。

### 决策

**D1. 流程结构：4 幕分块（来自 A，修补分组漏洞）**
- 4 幕对应 S/F/B/W 四个维度模型组，各 6 题（Act IV 含门控+触发共 8 题）。
- **幕内强制打散**：每幕 6 题 = 3 正向 + 3 反向，正向在前反向在后，且同维度正反间隔 ≥2 题。
- 重排在**前端 RenderQueue 层**完成（不改 DB order 字段），由 `flow_structure` feature flag 控制，默认 `"acts"`，可回退 `"linear"`。
- 来源：A 的主干 + 修补 A 未识别的"题序非按模型聚类"问题。

**D2. 幕间反馈：渐进式维度氛围词揭示（来自 C）+ 提问式审判官批注（来自 A）**
- 3 个幕间过渡层（Act I→II、II→III、III→IV），每个含：(a) 幕标题卡片；(b) **因子共鸣氛围词**——基于已答维度分输出氛围词（如"侵蚀加深""羁绊觉醒中"），**绝不输出角色/群体/百分比**，机器校验防剧透；(c) 审判官提问式批注 + 2-3 选项，**不计分**。
- 过渡层独立于 700ms 单题动画，寄生于 flushPending 之后的叠加层，默认 1.5s 可点击跳过。
- ResonanceEngine 输出维度级氛围词的映射表需实现者设计（C 未提供细节），约束：只读已答维度，不跨维度推断，不触及角色向量。

**D3. 第二人称选项：括号内心独白（来自 A）**
- option label 统一改为括号包裹的"你"的内心独白，主语"你"，去祈使动词，保留感受判断，分数不动。
- 符号按 locale 调整（zh 用全角括号，en 用半角，ja 用「」或全角）。
- 改 DB 的 Option.label + Question.translations（4 语言），**不是改 quiz-content.ts**。

**D4. 直问题：不计分纯叙事（来自 A，否决 B 的计分替换）**
- 3 个直问题嵌在幕间过渡层（与 D2 共用），不计分、不进 dimScores、不影响 match。
- **不替换任何现有反向题**，维度覆盖维持 12×2。否决 B 的"加3删3+归一化"以守 R4。

**D5. 题序重排：前端 RenderQueue 确定性重排（来自 A，否决 B 的动态）**
- 分幕顺序确定性（S→F→B→W），幕内按 D1 打散规则。无 clarity 动态排序。
- localStorage 仅存 currentIndex（与现状一致），不存 adaptiveOrder。
- 来源：A 的确定性 + 否决 B 的动态（不可复现、门控锚点风险）。

**D6. 门控/触发：保留原位（否决 A 的挪到 Act IV 末、B 的绝对位25/26）**
- 门控（题18位）、触发（题19位）保留原数组位置，作为分幕结构中的"最终审判"叙事节点自然融入。
- gateValue/triggerFired 逻辑、applyGateBonus、条件渲染全部零改动。
- 理由：挪动门控位会改变用户疲劳度下的关键决策，影响特殊角色触发率，无方案分析过此连锁。

### 后果
**得到**：分块完成感（A）+ 渐进式自我揭示获得感（C）双杠杆；零算法/时序风险；可回退（前端 flag + DB 备份）；R4 信度守住（不替换反向题）。
**牺牲**：失去 B 的自适应深挖收益（但该收益无数据支撑，且 R8 是可选）；幕间过渡增加约 4.5s 总时长（3×1.5s），需靠感知提速抵消；4 语言内容重写是关键路径瓶颈；氛围词映射表需从零设计（C 截断未提供）。

### 实现优先级
1. **P0（先做，可独立验证）**：D3 第二人称选项改造（仅 DB 内容，4 语言，最高 ROI，零结构风险）。
2. **P1**：D1+D5 前端 RenderQueue 分幕重排（含 D6 门控原位适配），feature flag 控制，可 A/B。
3. **P2**：D2 幕间过渡组件 + 氛围词映射表（依赖 P1 的分幕结构）。
4. **P3**：D4 直问题内容（嵌在 P2 过渡层内）。
5. **P4**：A/B 实验设施 + GA 监测（完成率/放弃率/单题时长）。

明确不动：match.ts、answer-processor.ts（D4 不计分故不动）、api/match/route.ts、api/quiz/route.ts、700ms 时序常量（feedbackDelay=400/totalDelay=700/cubic-bezier/is-dimmed）。
