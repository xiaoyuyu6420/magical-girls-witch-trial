# 「组件化·按 32 重组」技术设计

## 1. BLUF

这个变体的核心立场：**组件拆分的边界画在「renderType 分发层」和「视觉层宿主」，而不是画在「桌面/手机变体」上**。桌面挤压与手机赛博哥特是 CSS media query 的事，不是 props 的事——一个 `OptionButton` 渲染一个 `<button class="opt-block">`，两种视觉由 `@media (hover:hover) and (pointer:fine)` vs `@media (max-width:768px)` 各自接管，正如现有代码已经做的那样。承重决策是**保留所有 E2E 锚定的 class 名**（`.opt-block`/`.q-text`/`.result-layout`/`.weight-stage` 等），只为 32 的**新增**结构元素采用 32 的 class 名（`.hud-capsule`/`.editorial-grid`/`.tarot-card-frame`/`.stat-bars-container`/`.btn-neo`/`.aurora-burst`）——因为组件边界是 React 内部的事，与 DOM class 契约正交。最大单一风险：TestScreen 单体里的状态机（timer 驱动的 flushPending、批注去重 ref、weight 编码）在抽组件时若被误改时序，E2E 全套崩——必须把状态机留在 orchestrator，叶子组件做成纯函数。

## 2. 核心抽象（5 个承重边界）

> 不是 12 个组件——是 5 个**边界决策**，其余（OptionButton/BalanceScale/WeightMatrix/HUDHeader/TarotFrame/VerdictCard/PostureBars/ResultActions）是这些边界下的叶子。

### 抽象 1 — `TestStage`（orchestrator，TestScreen 瘦身后的残骸）
**承载什么**：答题状态机——`currentIndex`/`answers`/`gateValue`/`weightSlots`/`interjection` 去重（`shownInterjectionsRef`）、timer 驱动的 `flushPending`（700ms 桌面 / 680ms 触摸）、键盘映射、localStorage 持久化、`onComplete` 提交。
**关键约束**：所有时序逻辑**留在这里**，绝不下沉到叶子组件。叶子只收 props + 发 callback。
**为什么承重**：现有 TestScreen 650 行里，状态机是 E2E 全套（117 用例）的隐式契约——`handleSelect` 的 400ms toast、`feedbackDelay`/`totalDelay`、`flushPending` 的 isLast 分支、批注在 `answers.length===5/10/15` 触发且用 ref 去重防无限重开。这些动一个数字 E2E 就 flaky。抽组件时这层必须 1:1 搬迁，不做"顺手优化"。

### 抽象 2 — `OptionArea`（renderType 分发器，回答变体核心问题）
**承载什么**：`renderType` → 组件的路由：`scale`→`BalanceScale`、`weight`→`WeightMatrix`、default→`OptionButton` 列表。对应现有 `renderOptions()` 的 switch。
**这是变体核心问题的答案**：「桌面挤压/手机赛博哥特在哪里分叉？」——**不分叉**。`OptionArea` 渲染**唯一一棵组件树**，变体由 CSS media query 决定。`OptionButton` 无 `variant` prop。
**为什么这样画边界**：桌面与手机的差异是**视口**属性，会随 resize/设备旋转变化；如果用 props 表达，resize 时要重渲染 + 切换组件树，且无法覆盖"桌面触屏笔"等混合输入。media query 是浏览器原生、免费、连续的。现有代码（globals.css L411 `@media (hover:hover) and (pointer:fine)` vs L840 `@media (max-width:768px),(pointer:coarse)`）已证明这套可行——本变体只是延续。

### 抽象 3 — `VisualLayerHost`（非交互视觉层宿主）
**承载什么**：`ParticleCanvas`（45 粒子 rAF）+ `EmbossedWatermark`（题号 `01..26`）+ `AuroraTransition`（Q26 极光爆裂）+ 现有 `grain-overlay-test`。全部 iframe 内挂载（R31）、全部 `prefers-reduced-motion` 受控（R3/R30）。
**为什么承重**：32 的"招牌层"（粒子/浮雕字/极光）是这次新增的最大体量，且都是非交互、z-order 敏感（粒子 z1 < 浮雕 z2 < 内容 z10 < 极光 z200）。把它们收进一个宿主，保证：(a) 生命周期统一（mount/unmount 一起），(b) 永不误入交互树的 z-index 战争，(c) reduced-motion 一处门控全部。rejected：散落在 TestStage 各处——会重复 reduced-motion 检测且 z-index 难管。

### 抽象 4 — `ResultLayout`（editorial-grid 容器，C2 关键修复点）
**承载什么**：`≥850px` → `grid-template-columns: 380px 1fr`（左 TarotFrame + 右 ResultDetails）；`<850px` → 单列。**强制 `min-height:100vh` + 允许滚动**，废除现有 `height:100vh; overflow:hidden`（R16 根因）。
**子结构**：左 = `TarotFrame`（3:4 金边 + 紫 glow + 五角星 SVG 占位 + 角色名）；右 = `ResultDetails`（res-ip-tag + 渐变标题 + tag-cloud/neo-chip + VerdictCard + PostureBars + ResultActions）。
**为什么承重**：这是 spec R15-R24 的全部落地，且是"桌面显示不全"用户痛点的直接修复。把 grid 容器独立成承重抽象，是因为 R16（可滚动）和 R15（分栏）必须**在同一层**一起保证——若分到两个组件，height 策略和 grid 策略会失配。

### 抽象 5 — `RevealSequencer`（揭晓时序，A2 接缝）
**承载什么**：现有 ResultScreen L90-210 的全部——`REVEAL_TIMINGS` stagger、skip（click/keydown）、`revealLayerOut` 淡出、focus 管理（A-F1）、`document.body.classList.add("revealed")`、reduced-motion 跳过。
**与极光的关系（A2 落地，见 §5）**：极光在**答题出口**（TestStage 作用域，Q26 选中后、ResultScreen 挂载前）播放；RevealSequencer 在**结果挂载时**（ResultScreen 作用域）播放名字揭晓。两阶段、不冲突。RevealSequencer 的视觉从 `#050308` 重皮为金紫黑，但**逻辑原样保留**。

## 3. 关键决策（含否决记录）

### 决策 1（边界策略）— `OptionArea` 按 renderType 分发，**不**按设备分
- **所选**：`OptionArea` 内部 switch(renderType) → OptionButton / BalanceScale / WeightMatrix。桌面/手机由 CSS 决定。
- **否决 A**：`OptionButton variant="desktop"|"mobile"` prop。**输因为**：视口属性不该进 props——resize 要重渲染、无法覆盖混合输入（触屏笔）、与现有 media-query 体系重复造轮子。
- **否决 B**：两个独立组件 `DesktopOption`/`MobileOption`。**输因为**：逻辑双份、状态同步地狱、E2E 要分叉两套选择器。

### 决策 2（class 命名）— 保留 E2E 锚点 class，新增元素用 32 名
- **所选**：交互元素保留现有 class（`.opt-block`/`.opt-index`/`.q-text`/`.q-meta`/`.balance-pan`/`.weight-stage`/`.weight-card`/`.btn-confirm-weight`/`.interjection-overlay`/`.result-layout`/`.r-name`/`.r-slogan`/`.r-desc`/`.r-actions`/`.btn-restart`/`#progress-line`/`.watermark-index`）。**新增**结构元素用 32 名（`.hud-capsule`/`.progress-track`+.progress-fill/`.card`/`.tag-pill`/`.pulse-orb`/`.aurora-burst`/`.bg-typography`/`#bg-canvas`(粒子)/`.editorial-grid`/`.tarot-card-frame`/`.neo-chip`/`.verdict-editorial-card`/`.section-label`/`.stat-bars-container`/`.stat-fill`/`.btn-neo-primary`)。
- **原因**：E2E 全套（117 用例 + helpers）零 `data-testid`，纯靠 class 定位。保留锚点 = 选择器零回归；新增元素无碰撞 = spec §2 的 DOM 断言（`.hud-capsule`/`.editorial-grid` 等）直接满足。
- **否决**：全量采用 32 的 class 名（`.opt-btn` 替 `.opt-block` 等）。**输因为**：要重写 ~30 处 E2E locator（quiz/keyboard/reveal/helpers 都用 `.opt-block`），且 spec V8 的验收方式只断言 `.opt-index` 文本格式（不断言 `.opt-btn`）——保留 `.opt-block`+`.opt-index` 同样过验收。**标注**：这是低风险默认；若 spec 作者坚持要 `.opt-btn`，成本是 +30 处选择器改写，不承重。

### 决策 3（双变体机制）— CSS media query，**不**用 props/JS 检测
- **所选**：延续现有 `@media (hover:hover) and (pointer:fine)`（桌面挤压，globals.css L411）vs `@media (max-width:768px),(pointer:coarse)`（手机赛博哥特，L840）的双作用域。配色 token 统一为金紫黑（`--gold-hyper:#FFD700`/`--purple-neon:#D800FF`/`--violet-deep:#7B2CBF`/`--rose-crimson:#FF0055`/`--bg-void:#030305`），香槟 `--champagne-*` 24 处引用全部 remap。
- **原因**：现有 CSS 已是这套双作用域架构且 E2E 绿；本变体只换 token 值，不改作用域边界。A3（挤压 selected 用金紫渐变 + 中性灰 dimmed）让两端 selected 视觉**收敛**，进一步收窄双变体差异面。
- **否决**：JS 检测 `matchMedia('(pointer:fine)')` 在 React 里设 state 切变体。**输因为**：SSR 不安全（现有 TestScreen 用 ref 存 touchFeedback，仅用于震动反馈时长，不用于渲染分支），且与 CSS 作用域双重真相易漂移。

### 决策 4（状态归属）— 状态机留 orchestrator，叶子纯函数
- **所选**：`TestStage` 独占 `currentIndex`/`answers`/`timer`/`interjection` 去重。`OptionButton`/`BalanceScale`/`WeightMatrix` 收 `(option, index, selected, dimmed, disabled)` 发 `onSelect(option)`。`WeightMatrix` 的 `weightSlots` 状态**留 TestStage**（因为编码 `weight::a|b|c` + handleWeightConfirm 依赖 current.options，跨组件状态会断裂），WeightMatrix 只负责渲染点阵 + 发 `onCycle(slotIdx)`。
- **原因**：timer 时序（700ms flushPending）和批注去重（ref 防 answers.length 不变重开）是 E2E 隐式契约，下沉到叶子必然失配。
- **否决**：每个题型组件自管状态。**输因为**：weight 编码要在提交时查 `current.options`（TestStage 才有），状态分散后要回传，时序不可控。

### 决策 5（转场接缝）— 极光替换 quiz-exit 间隙，Reveal 保留重皮
- **所选**：Q26 选中 → TestStage 触发 `AuroraTransition`（800ms scale 1→250）→ 同步发起 `/api/match`（page.tsx）→ match resolve + 极光结束 → ResultScreen 挂载 → RevealSequencer 播名字揭晓（重皮金紫黑）。极光与 match fetch 并行，谁慢等谁（极光 min 800ms，match 通常 <500ms，故极光占主导）。
- **原因**：现有 quiz→result 间隙是空白 + loading spinner（page.tsx L201-229），极光替换它天经地义；Reveal 是 ResultScreen 内部的名字揭晓时刻，承载 focus/body-class/skip 非视觉职责，删了丢功能。两阶段不重叠。
- **否决 A**：极光叠加在 Reveal 上（A2 读法 B）。**输因为**：两层动效竞态、z-index 冲突、用户要"和 32 一样"而 32 只有一层。
- **否决 B**：删除 Reveal 全部逻辑，极光承担揭晓。**输因为**：丢 focus 管理（A-F1）、body.revealed class、skip——E2E（result.spec.ts "reveal sequence plays and can be skipped"、reveal.spec.ts）会崩。

## 4. 被拒绝的替代方案（变体级）

1. **拒绝「12 个扁平组件全平铺」**：spec 列了 12 个组件名，但全平铺会让 TestStage 直接编排 9 个孩子、ResultStage 编排 6 个，orchestrator 退化成 props 转发站。本变体归并为 5 承重边界 + 叶子，orchestrator 只编排 4-5 个承重组件，叶子由承重组件内部组合。
2. **拒绝「按 32 的 class 名全量重命名 DOM」**：见决策 2 否决。会触发 30+ E2E 选择器重写，且 spec 验收不强制。
3. **拒绝「把极光和 Reveal 合并成单一 TransitionController」**：一个跨 TestScreen/ResultScreen 生命周期的全局控制器，违反"组件边界对齐作用域"原则——极光是 TestStage 出口事件，Reveal 是 ResultStage 入口事件，强行合并会引入跨组件状态耦合，且无法独立测试。

## 5. 主要风险（≤3，按风险排序，含缓解）

### 风险 1（最高）— 状态机抽离时序漂移 → E2E 全套 flaky
**具体**：TestScreen 的 `flushPending`（400/700ms timer）、`feedbackDelay`（320/400ms 触摸/鼠标）、批注 `shownInterjectionsRef` 去重、weight 编码 `weight::a|b|c` 是 E2E 117 用例的隐式时钟。抽 `OptionArea`/`WeightMatrix` 时若把 `handleSelect` 的 setTimeout 误移到叶子，或 weightSlots 状态下沉，时序错位 → quiz.spec/reveal.spec/keyboard.spec 集体 timeout 或断言失败。
**缓解**：(a) 状态机（timer/refs/编码逻辑）**强制留 TestStage**，叶子只发 callback（决策 4）；(b) 抽离后先跑 `pnpm playwright test tests/quiz.spec.ts tests/reveal.spec.ts tests/keyboard.spec.ts` 三件套验证时序，再动视觉；(c) E2E helpers 不改（它用 `.opt-block,.balance-pan` 聚合定位，class 保留即兼容）。

### 风险 2（高）— 视觉基线强制全量重生成，无法当回归网
**具体**：`tests/visual/__screenshots__/` 有 7 张基线（test-desktop/test-mobile/result-profile/welcome×4），本次配色从香槟→金紫黑、结果页从米白单栏→深色分栏，**每一张都会 diff**。这意味着视觉测试在本次任务里**不是回归保护，是交付物本身**——重生成前无法用它抓中间态回归。
**缓解**：(a) 接受基线重生成是计划内步骤（非意外漂移），在全部视觉改完后一次性 `--update-snapshots`；(b) 重生成**前**用 E2E（选择器契约，决策 2 保证兼容）+ Vitest（数据层不变）作为过渡回归网；(c) 重生成后立即锁定，后续改动靠它防漂移。这不是本变体特有风险（任何变体都要重生成），但组件化变体尤其要警惕：叶子组件单独看好看 ≠ 组合后基线稳——重生成后要跑二次验证。

### 风险 3（中）— 32 新增 class 与现有 class 的 CSS 特异性冲突
**具体**：globals.css 现有 `.opt-block.is-selected`（L417，特异度 0,2,0）与手机作用域 `.opt-block.is-selected`（L877，0,2,0 + 媒体块内）。新增 `.aurora-burst`/`#bg-canvas`/`.bg-typography` 的 z-index（1/2/200）若与现有 `.view-test::before`（z40）/`#progress-line`（z9999）冲突，会出现粒子盖住选项或极光被 progress-line 压住的 bug。
**缓解**：(a) 新增视觉层 z-index 严格按 32 原值（canvas z1 < bg-typography z2 < 内容 z10 < aurora z200），与现有 progress-line z9999 不撞（progress-line 在最顶是既有设计）；(b) `VisualLayerHost`（抽象 3）集中管理 z-index 常量，禁止叶子自定义；(c) 手机作用域的 `.opt-block` 规则（L840 媒体块）保持源序在桌面规则之后，维持现有覆盖关系。

## 扩展点

- **留开放**：`OptionArea` 的 renderType 分发是开放枚举——未来加新题型（如滑块题）只需加一个 case + 一个叶子组件，不动 TestStage 状态机。`VisualLayerHost` 的 children 是数组——未来加星座连线层只需 append。
- **关闭（YAGNI）**：`OptionButton` 不做 `variant` prop（决策 1）；不做第 6 角色 mami_facade（spec 明确非目标）；不做 en/ja/zh-TW 翻译（spec 明确）；不把 Reveal 抽象成通用 transition 框架（只有一处用，YAGNI）。

## 不确定性标注

- **决策 2（保留 .opt-block 不改 .opt-btn）**：低风险默认。spec V8 验收方式只断言 `.opt-index`，但 32 实现细节列了 `.opt-btn`——若验收者严格要求 `.opt-btn`，成本 +30 选择器改写，不影响架构。
- **A2 极光 handoff 时序**：极光与 match fetch 的 `Promise.all` 是我的推荐，但 match fetch 实际耗时未实测——若 P95 >1.5s，极光 hold 会显得卡，需备 fallback（极光播完显示静态金紫底 + 小 spinner）。建议实现时先埋点测 match P95。
- **A4 分享卡**：我落地按深色，但显式标注"需用户拍板"，不替用户决定。
