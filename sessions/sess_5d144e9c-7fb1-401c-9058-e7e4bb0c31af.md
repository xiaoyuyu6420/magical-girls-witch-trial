## 结论

首页不是 Next.js 渲染的，是 rewrite 到 `public/index.html` 的纯静态页，内联脚本不经任何编译/降级。它同时跑着这几样东西，X5（老 Chromium，很多设备还停在 66~86 水平，GPU 光栅化和合成很弱）全部踩中：

**卡的主因（按权重排序）**
1. **全屏 feTurbulence 噪点层**（`index.html:98`）：整页背景是运行时 SVG 分形噪声（baseFrequency 0.95 + 3 octaves）。老内核光栅化它走软件路径，全屏铺开一次就非常贵，这是移动端老内核出名的卡顿源。
2. **Canvas2D 全屏 60fps 重绘**（`#abyss-canvas`）：约 1300 个粒子每帧逐个 sin/cos + `arc/fill`，X5 的 Canvas2D 在不少机型上没有 GPU 加速，直接把帧率打崩。
3. **合成层叠加**：巨字 `mix-blend-mode: exclusion` + `-webkit-text-stroke` + 全屏 vignette 渐变 + `backdrop-filter`（X5 老版本不支持 backdrop-filter，只会视觉降级；较新版本支持但更卡）。
4. **三个常驻 rAF 循环**：粒子动画、光标跟随，还有一个 `updateTime` **每帧往 DOM 写 innerText**（每秒约 60 次强制文本更新），纯浪费。

**背景动效"显示不出来"的机制**
开场有个 boot 序列：加载进度条 → "ACCESS GRANTED" 乱码动画播完 → 才调用 `startRingExpand()`。而展开动画没启动时（ringExpand=0），每个粒子都被 `if (t < 0.04 ...) continue` 跳过——**canvas 上什么都不画**。在 X5 上主线程被上面那堆东西卡死，乱码动画掉到几 fps 走不完，`startRingExpand()` 迟迟不触发，于是你看到的就是黑底 + 文字、背景全无。桌面 Chrome 性能强，同样代码完全看不出来。

## 修复选项

- **A. 首页性能大扫除（推荐）**：噪点层换成预烘焙的 PNG（视觉一样、代价归零）；`updateTime` 改 250ms interval；三个 rAF 合并成一个；loader 加 2.5s 超时兜底（乱码卡住也强制进主画面）；canvas 降半分辨率渲染 + 低端机减粒子密度。所有手机都受益，工作量中等。
- **B. 只做 X5 定向降级（最快）**：UA 里检测到 `MQQBrowser` 就关掉粒子动画，换一帧静态星点 + CSS 光晕，其他不动。改动小，但其他安卓低端机照旧卡。
- **C. 什么都不改，页面上提示"用系统浏览器打开"**：收益最大但体验最糙，不建议单独用。

我的建议是 A（顺带把 B 的 UA 降档包进去）。你拍个板，我就动手。

## 👤 用户

## 🤖 助手
不是。打包发生在 **GitHub Actions 的云端机器**上，服务器只负责“拉现成镜像、重启容器”，全程不做任何编译构建。

完整链路：

```
你本地 push → GitHub Actions（免费云端 runner）
                ├─ npm install + lint + test
                ├─ docker build（在 runner 上跑 next build 打出镜像）
                └─ 推镜像到 Docker Hub
                        ↓
            服务器只执行两条命令：
                docker compose pull   ← 下载打包好的镜像
                docker compose up -d  ← 重启容器
```

所以刚才磁盘满的原因**不是**服务器打包产生的构建缓存，而是：每次部署都从 Docker Hub 拉一个新镜像层（latest 一直更新），旧的镜像层留在服务器上从不清理，加上每次部署留一个 compose 备份文件——十几次部署就把盘吃光了。现在 update.sh 每次部署前自动 `docker image prune` 清掉不再使用的旧镜像，这个问题已经根治。

服务器本身很轻：容器限了 1 CPU / 512M 内存，只跑 Next.js standalone 产物 + SQLite，构建压力全在 GitHub 那边（私有仓库每月 2000 分钟免费额度，今天这轮折腾用得比较多，但正常节奏完全够用）。
