## 数据流 / 重写流程（写 → 校验 → 修复 的循环组织）

```
阶段0 铸尺（orchestrator，一次性）
  tar.gz ──> CopySnapshot 三份 JSON + hash ──> git 提交 ──> G6 自检（旧文案必红、3 题黄金样例必绿）
阶段1 zh-CN 定稿（四轮批次）
  题库批 ×5（5-7 题/批）──> 角色批 ×5（4-5 角色/批，16 witch-trial + 5 madoka）──> i18n 批 ×1（zh-CN UI 键）
  每批内部循环：
    implementer 写 ──> 跑 GateSuite（--phase zh --scope 当批）──> 硬门挂：自己修，≤3 轮 ──> 硬门全绿
    ──> orchestrator：审软警告 + 抽 2 题做调性抽检（对照 REDESIGN 标杆）──> 签字 ──> 下一批
阶段2 l10n（三批：en/ja/zh-TW 各一批）
  翻译 agent 写 ──> GateSuite（--phase l10n：G3 翻译残留 + key 集合 + 非空）──> 修复轮
阶段3 终检（独立 QA agent，非 implementer）
  全量跑 G0–G6（不传 --scope，不传 --phase）──> 全量 ReviewChecklist ──> 跑现有 seed + 集成测试
  ──> 用户终审（只看清单 + 抽读，不逐字审）
```

**谁在循环里**：
- **implementer**：写文案 + 跑闸 + 自己修复（≤3 轮）。责任边界：让硬门绿、把软警告清到自己觉得没问题的程度。它无权改 GateConfig，无权跳过某道闸。
- **orchestrator**（父 agent）：铸尺（阶段 0）、逐批签字、裁决 unclear 逃生通道、批准任何阈值改动。硬门由它做权威复核（implementer 的本地跑不算数）。
- **独立 QA agent**：阶段 3 全量复跑 + 人审清单定稿——它没写过任何文案，不存在自证清白问题。
- **用户**：只在阶段 0 看 3 题黄金样例（校准调性锚）和阶段 3 看终审清单。这是"把每一步变成闸门"的直接结果：人从逐字审稿里被解放出来。

**循环纪律**：不修完当批不进下批；修复超过 3 轮 = 批次规格有问题（要么题太难要么范围太大），停下来拆批而不是硬写；软警告不要求全清，但每条都要有处置（修 / 承认不修 + 一句理由）——处置记录进 ReviewChecklist，这是防"软门形同虚设"的机制。

## 关键决策（7 条，归 3 类）

### 类别 A：校验架构
- **A1 快照先于重写（diff 只对快照）** → 重写第一步就是从 tar.gz 一次性提取 CopySnapshot 并提交
  - **原因**：tar.gz 是"会动的参照物"（路径/内容/被谁重新打包都不可控），快照是冻住的基准，diff 可复现、可审计；寄存器标签在快照阶段经过一次人工核验，错误不会在重写中途才爆出来。
  - **否决**：直接在循环里每次解压 tar.gz 对照——被否决：无法保证基准不变，且每次解压成本会让 implementer 找理由跳过对照；寄存器打标靠 LLM 每次现打——被否决：同输入不同输出，闸门不可复现。
- **A2 单入口 + 硬/软双级门** → 一个 CLI、退出码说话、无挑闸门选项
  - **原因**：契约里"0 次 / ≤3 次 / 全部分岔 / 全部逼问"是数字，数字就该硬；"人味"写不出数字，写不出数字的东西硬门化必然误伤，所以质感降级为软警告进人审。硬软边界 = 契约量化项 vs 非量化项，判据清晰，不是拍脑袋。
  - **否决**：全部软门（"都给 review agent 看"）——被否决：等于没有门，重写循环退化成信任流，契约 10 条判定无人执行；全部硬门——被否决：细节信号这类代理指标会误杀好文案，循环会被假阳性拖死。
- **A3 "语义倾向不变"用寄存器↔score 映射代理** → G4 只验极值位的寄存器方向
  - **原因**：score 冻结 + 寄存器方向一致 = "承认的还是承认的"，这是能在不引入外部判断的前提下给到的最强语义保证；unclear 逃生通道承认了代理的边界。
  - **否决**：LLM 语义相似度门（"新选项与旧选项意思一致度 ≥0.8"）——被否决：不可复现、阈值不可解释、且会把"重写"变成"换皮"（离原文越近分越高，与去模板化目标直接冲突）；人工逐题核对——被否决：这正是要消灭的 26 题逐字审。

### 类别 B：文案边界
- **B1 砝码题 label 冻结为结构字段** → `weight::a|b|c` 编码逐字节对照快照，不进重写范围
  - **原因**：编码是渲染的输入（槽位分配），它占着"label"这个看起来能改的位置；契约的逻辑字段清单没列它，是 spec 沉默——选了"冻结"这个保守默认，并显式标注。
  - **否决**：当作普通文案重写（"改成人话"）——被否决：打断砝码渲染/落库，违反"结构锁死"总原则；把编码挪到新字段——被否决：改 schema，超出非目标红线。
- **B2 四语言死代码数组删除（不保留标注）** → i18n 里 questions/gate/trigger 数组直接删掉
  - **原因**：这份死代码已经坑过一次（zh-CN 88-131 行残留旧文案，R1 说它不参与渲染——谁知道哪天有人又填它）；清空后它连"历史参考"价值都没有（历史在 git 和备份里），留着 = 一个永远在引诱人填错地方的陷阱。
  - **否决**：保留 + 加大注释——被否决：注释防不住人，上次的注释现在就在，尸体还在；移到独立参考文件——被否决：等价于保留，且多一个文件多一份漂移面。
- **B3 契约沉默处选冻结默认** → `name`/`subtitle` 不进可改清单（改=违规，校验器锁死）；`meta` 属可改文案字段（契约 R2 明列）
  - **原因**：可改清单（text/label/slogan/desc/keywords/meta）和逻辑清单都没列 name，就冻结——角色名是标识符不是文案；meta 在可改清单里，允许重写但保持其"题型标签"角色。低风险默认，已标注。

### 类别 C：流程
- **C1 逐批小循环 + 阶段闸 + 翻译残留闸** → 5–7 题/批、implementer 自跑自修 ≤3 轮、orchestrator 逐批签字；l10n 阶段加 G3 翻译残留检查（en/zh-TW 无 CJK、ja 不与 zh 逐字相同）
  - **原因**：修复成本与批次粒度成正比——26 题一次性写完，若 G1 命中 15 处模板，implementer 面对的是"重写全文"而不是"改 2 行"；5–7 题/批也正好是一轮上下文能承载并保持调性一致的量。
  - **否决**：全量写完再一次性校验——被否决：修复成本线性膨胀、违规定位模糊（哪批引入的？）、且一次 26 题长文输出的调性必然漂移；每 1 题一批——被否决：闸门开销比写作开销还大，循环空转。

## 人审保留点（自动校验测不了，必须留给人或独立 agent）

诚实清单——G0–G4 能保证"结构没坏、数字达标、方向没反"，以下四类它**结构上**测不了：

1. **调性是否真的到位**。G2 只能确认"有反问标记/有问号"，测不了"这句话有没有让人后脊发凉"。逼视感是 REDESIGN 全部技术手法的落点，也是本次重写的头号目标——代理指标在它面前必然失明。处置：每批抽 2 题，由 orchestrator（或独立 review agent）对照 REDESIGN 的 F1 标杆逐句评；抽检不合格当批打回。
2. **三态的语气区分度**。"承认是否真的痛、否认是否真的硬、中间是否真的复杂"——G1 只测了三个选项长得不像，G4 只测了承认还在承认位；语气对不对是语感问题。处置：ReviewChecklist 固定项，逐批抽查三态互读（把三句连读，是否像同一个人的三种回应）。
3. **细节的可信度**。"记得当时的天气"是具体指控，"记得很多事"是空话——G2 的细节信号计数两者都加分。这是代理指标与真值的最大裂缝。处置：人审固定项，凡 G2 细节信号=0 的题人审必看；信号≥1 的题按 20% 抽读。
4. **角色文案与角色本体（向量）的契合度**。"HIRO 的 desc 是否真的写出了复仇+执念"——机器可以数关键词，判断不了"这个角色读起来像不像他自己"。跨 IP 撞设（EMMA/MADOKA）的比喻分岔是否真的分开了，也是语感问题。处置：人审固定项，向量↔文案对照抽检（16+5 中抽 8）。

另外两条人审边界，提前声明：**软警告清不清是 orchestrator 的判断不是机器的**（处置记录机制已设计）；**unclear 逃生通道的裁决权在 orchestrator**，机器只负责标记。

## 被拒绝的替代方案

1. **全量后置校验**（先写完 26 题 + 21 角色 + 四语言，最后一次性跑校验修）——被拒：修复成本随批次线性膨胀（一处模板化命中就要回炉整批记忆），违规无法定位到引入批次，26 题单次长输出调性必然漂移。它省的是闸门开销，赔的是整个循环的可控性。
2. **LLM 评审门**（每批让一个独立 agent 打分，低于阈值打回）——部分采纳（作为 G5 软警告 + 人审抽检的形态存在），但**拒绝**作为硬门：LLM 打分不可复现（同文案两次跑可能不同分）、阈值不可解释（凭什么 3.2 分过 3.1 分挂）、且与模型的文化审美偏好耦合——它会成为"看起来最像质检、实际最没法审计"的闸。让它当硬门等于把验收外包给一个不可审计的黑盒；让它当软门，它的意见才有价值。
3. **纯 grep/shell 一次性脚本**（校验逻辑散在 `node -e`、`grep -c` 里）——被拒：不可复现、不可版本化、implementer 在循环里无法稳定复用，且"检查本身有没有 bug"无人负责。收敛为单一工具集 + 单一配置 + G6 自检，校验器本身也成为被测对象。

## 主要风险（3 个，按严重度）

1. **寄存器检测误判拖死循环**（G4 的核心假设）——新文案若刻意抛弃旧标记（"你说得对"被限流后，承认句可能不再带可识别标记），要么假阳（好文案被拦，循环卡死），要么假阴（unclear 逃生通道被滥用成后门）。**缓解**：只校验极值两点的方向、unclear 只能降级为软警告不能静默放行、阶段 0 用 3 题黄金样例校准词表、G6 负样本保证旧文案必红——四层防线，任一失效都有信号。
2. **Goodhart 效应：文案向校验器过拟合**——implementer 写出"有反问标记、没逼视感"的合规但无味文案，校验器全绿，重写白做。这是把质量量化必然招来的鬼。**缓解**：结构性预防——质感类指标全部软门（不给过拟合提供目标函数）、每批人审抽检 2 题（机器绿不等于人眼绿）、G5 的高频词表反向监视（当"对吧"成为新模板时 G1 的相邻句式闸会抓到它）；若抽检连续两批不合格，暂停循环重校黄金样例，而不是调阈值。
3. **快照与实现漂移**——快照在阶段 0 冻结，但若中途有人动了逻辑字段（seed 重跑、加题、调 score），G0 会对着旧快照误报，循环被无关失败淹没；反过来若有人悄悄改了快照，所有闸一起失明。**缓解**：快照一次性提交 + hash 记入 STATE.md + 任何重生成是显式记录动作（留 diff 审计）；G0 报告里对"快照 vs 备份 tar.gz"也做一次冷启动校验（提交时验一次，证明快照没有生成错误）；循环期 72h 内代码 mtime 变更触发告警（沿用 STATE.md 的 staleness 机制）。

## 扩展点

- **留开放**：GateConfig 的 `[tunable]` 阈值和词表——后续每轮重写（新 IP 接入、新语言）只需改配置不改校验器；G4 的寄存器词表未来可扩成"三态语气强度"分级（软）；G5 的质感信号将来若积累出可复现的坏文案样本库，可以把单项从软门升级为硬门——升级条件是"负样本回归覆盖它"，这个条件本身就是防滥用闸门。
- **关闭（YAGNI）**：不做 LLM 评分硬门（不可审计，见否决 2）；不做文案质量仪表盘/趋势图（26 题 × 4 语言是单次战役，不是持续运营，批处理报告足够）；不做校验器的增量/缓存（每批全量跑，26 题规模毫秒级完成，缓存引入的复杂度不值）；不做 i18n key 的类型级锁（key 集合一致性已被 G0 运行时锁住，类型锁与运行时锁重复，且跨语言 key 漂移只有运行时 diff 抓得住）。
