### 意图契约（EARS）

#### 核心意图
在不动摇"服务端重算、16 人格、门控/触发/兜底"这套既有能力的前提下，消除测试在**答题顺序/选项结构/结果暴露面**上的"算法可读性"，让用户无法凭直觉或简单请求逆向出计分规则，同时维持结果的可信度与沉浸感。

#### 需求（EARS）

**A. 答题过程不可识破**

- **R1** WHEN 用户连续作答任意 3 道常规题，THE SYSTEM SHALL NOT 让用户能从选项顺序或措辞中稳定推断出"靠后的/更激进的选项 = 更高分"。`[假设：通过"每题选项顺序与分数方向不再恒定一致"达成，而非改变分数本身。具体手段由设计阶段定]`
- **R2** WHEN 题目按顺序呈现给用户，THE SYSTEM SHALL NOT 让"前 12 题 = 12 个维度各一题、后接反向校验"这种结构性节奏在题面/进度上可被肉眼识别。`[需澄清：是打散顺序即可，还是允许加入与计分无关的"叙事/氛围题"来打断节奏？]`
- **R3** WHERE 同一维度有正反两道题，THE SYSTEM SHALL 确保反向题在**计分层**真正反向上分（即反向题的"高分选项"应对应该维度的低档），而非仅在措辞上反向。`[假设：当前 `Q()` helper `score: i+1` 导致反向题并未真正反向——这是 bug，应修复]` `[需澄清：是否确认 spec 第 4 节"第 2 题做反向校验（措辞方向与第 1 题相反）"指的是计分反向而非仅措辞反向？]`

**B. 结果呈现保留沉浸、不摊开算法**

- **R4** WHEN 结果页向用户展示匹配结果，THE SYSTEM SHALL NOT 默认把"12 维向量字符串（userVector/templateVector）、加权距离、档位数值"等算法内部量直接以技术形式呈现给用户。
- **R5** IF 结果页仍要展示维度分析或相似角色对比，THEN THE SYSTEM SHALL 以"叙事化/游戏化包装"呈现（如"因子倾向"而非"维度得分"），且不暴露能反推权重/阈值/距离公式的数值或结构。`[需澄清：雷达图、维度条、top3 百分比这三样，保留哪些、砍掉哪些、包装成什么——这是核心分叉]`
- **R6** WHERE 相似度百分比被展示，THE SYSTEM SHALL 保证它表达的是"契合度/共鸣度"等沉浸语义，而非"加权曼哈顿距离换算结果"。`[假设：百分比数值本身可保留，但其呈现不应附带可反推公式的周边信息]`

**C. 服务端重算不可破坏（防篡改红线）**

- **R7** THE SYSTEM SHALL 始终在服务端从 DB 的 option 记录重新计算 `dimScores / gateValue / triggerFired`，前端提交的分数/向量/结果一律不信任。`[现有 answer-processor.ts 已满足，属既有约束，不得回归]`
- **R8** IF 任何"混淆/打乱"手段被引入，THEN THE SYSTEM SHALL 不削弱服务端重算的确定性——同一组 DB option 必须产出同一匹配结果。`[假设：混淆只发生在"呈现层 / 出题结构层"，不进入"计分层"]`

**D. 既有能力不可破坏**

- **R9** THE SYSTEM SHALL 保留 16 种人格（13 常规 + 1 兜底 + 2 特殊）的判定能力，包括门控题触发路径与触发题。
- **R10** WHEN 门控题选触发路径且触发题确认，THE SYSTEM SHALL 仍能正确返回对应特殊人格（相似度 100%）。
- **R11** WHEN Top1/Top2 差距过小且 Top1 偏低，THE SYSTEM SHALL 仍返回兜底人格（UNSET）；差距小但 Top1 足够高时标记"边界型"。`[需澄清：SPEC 的 Δ=8%/T=55% 与代码的 delta=3/threshold=40 哪个为准？这直接影响兜底频率]`

**E. 可维护性 / 可验证**

- **R12** WHERE 内容、权重、阈值需要调整，THE SYSTEM SHALL 让这些仍可在 `src/data/quiz-content.ts`（或同等集中位置）独立修改，不需改算法代码。
- **R13** THE SYSTEM SHALL 保留可自动验证的测试（vitest），覆盖：匹配确定性、兜底触发、特殊触发、反向题计分正确性、（新增的）选项顺序与分数方向不再恒定绑定。

**F. 信息暴露面收窄**

- **R14** WHEN `/api/quiz` 向前端返回题目与角色数据，THE SYSTEM SHALL NOT 返回能直接还原计分模型的服务端字段（如 `weights`、维度档位映射）给前端，除非该字段是渲染所必需。`[需澄清：`weights` 当前确实在返回——是否移除？`dimensions` 的 dir/model 字段是否算泄露？]`
- **R15** WHERE 前端需要展示维度，THE SYSTEM SHALL 通过受控的展示字段获取数据，而非在前端 import `parseVector` / `WEIGHTS` 自行解析算法内部结构。`[现有 ResultScreen 直接 import parseVector——属泄露面]`

#### 非目标（不做清单，从 spec/seed 提取，不发明）

- **NG1** 不改成纯随机/纯娱乐结果——匹配仍由算法驱动（seed 明确）。
- **NG2** 不放弃服务端重算与防篡改（seed 明确；R7/R8）。
- **NG3** 不把项目改造为通用 MBTI/性格测试平台（seed 明确）。
- **NG4** 不重写底层匹配算法（加权曼哈顿 + 门控触发）——本次是"让算法不被看穿"，不是"换算法"。`[假设：用户原话"不能让人一眼看出来算法"指的是隐藏现有算法，而非替换它]`
- **NG5** 不削减 16 人格的内容丰富度（slogan/desc/keywords 不动）。

#### 约束

- **C1** 技术栈锁定 Next.js 16 + React 19 + Prisma/SQLite（既有项目，README）。
- **C2** 匹配算法必须在后端 `/api/match` 执行，前端只展示（SPEC 9.3.1）。
- **C3** 答题明细存 Answer 表，不存 JSON（SPEC 9.3.2）——影响任何"加叙事题"的方案：叙事题要么也落 DB，要么明确不计分。
- **C4** 进度恢复用 localStorage（SPEC 9.3.3）——若打乱题目顺序，恢复逻辑需兼容。
- **C5** 4 语言（中/繁/英/日）——任何题面/包装改动需同步 i18n。

#### 成功标准（验收锚点）

- **S1** 给定一个不熟悉项目的普通用户，连续做完一次测试，无法仅凭答题过程说出"第 N 题测的是哪个维度""哪个选项分高"。（主观，可用人测验证）

### 歧义（分叉——先决定这些）

按对后续设计的影响排序：

**A1 — "看不出算法"的威胁模型**（最关键，决定一切方案的强度）
- 读法 A：只防**普通用户凭直觉识破**——重点改题面/选项顺序/结果包装，不动 API 字段。
- 读法 B：也防**技术用户逆向**——必须收窄 `/api/quiz` / `/api/match` 返回字段、移除前端对 `parseVector`/`WEIGHTS` 的依赖、结果不返回 userVector。
- **提问：** 这次改进要挡到哪一层？挡普通用户直觉就够了，还是要让会看 network 面板的人也逆不出算法？（我倾向 A+B 都做，但 B 是分水岭，因为它会动 API 契约）

**A2 — 结果页维度分析的去留**（决定 ResultScreen 改动幅度）
- 读法 A：**完全砍掉**维度条/雷达图/向量字符串，只留角色 + slogan + 描述 + 群体占比。
- 读法 B：**保留但叙事化包装**——"因子倾向"代替"维度得分"，雷达图改成"灵魂图谱"，不出现 L/M/H/X 和百分比反推。
- 读法 C：**藏到二级展开**（现状已部分如此：点"分析"才弹窗），但弹窗内容仍需去技术化。
- **提问：** 结果页的维度对比（雷达图/维度条）你想保留、包装、还是直接砍？（现状是默认隐藏在弹窗里，但弹窗里仍是裸的 L/M/H/X + 向量字符串）

**A3 — 主攻方向：题面 vs 算法**（决定工作量和回归风险）
- 读法 A：**以题面/选项结构为主**——打乱选项顺序、让分数方向不固定、打散题目节奏、修复反向题计分。算法核心不动。
- 读法 B：**也动匹配层**——比如引入非线性映射、维度交叉项、随机扰动，让结果更难反推。
- **提问：** 允许动到匹配算法本身吗，还是只允许动"题目怎么出、结果怎么展示"？（我推荐 A：算法不动，只动出题与呈现，回归风险最低且符合 NG4）

**A4 — 结果不可预测性 vs 匹配精确感**（决定是否引入扰动）
- 读法 A：**严格确定性**——同答案永远同结果，可信度优先。
- 读法 B：**允许轻微不可预测**——同答案在不同会话/时间有微小结果差异，换取"看不出算法"。
- **提问：** 允许结果带一点点不可预测性（哪怕牺牲一点点"角色匹配的精确"）吗？还是必须严格一一对应？（我推荐 A：保持确定性，R8 已锁定）

**A5 — 历史记录兼容**（决定是否要数据迁移）
- 读法 A：**兼容现有 TestRecord**——已存的历史结果解释不变，新逻辑只影响新测试。
- 读法 B：**允许重新解释**——历史记录可能需要标注"旧版结果"或忽略。
- **提问：** 已经测过的历史记录需要保持结果可解释吗，还是可以只管新测试？（影响任何改变向量/阈值含义的方案）
