# 排查教训：QQ X5 内核全站卡顿（2026-09-01 ~ 09-02，已结案）

一次持续两天的性能排查复盘。起因：用户在 QQ 内置浏览器（X5 内核）里全站极卡——首页乱码动画"一个字一个字变"、答题页 2 FPS；Edge 手机版正常。最终通过**隔离诊断页实测**逐步定位。

> **最终定案（09-02）**：v3 诊断页实测显示该设备 QQ WebView 为软件渲染——
> 纯文本零特效滚动只有 8 FPS；用户随后发现**百度和自己的另一个网站在同一 QQ 里同样卡**。
> 主因是用户设备的 QQ 应用（X5 WebView 组件）处于降级/软件渲染状态，与任何网站代码无关。
> 自救路径：更新 QQ / 关省电模式 / 清内核缓存 / 用系统浏览器打开。
>
> 代码侧的最终产出：
> 1. UA 定向降级（`html.x5`）：关 backdrop-filter / feTurbulence / 粒子 canvas——对真正的 X5 设备仍是净收益；
> 2. **低帧率兜底提示条**（不依赖 UA）：首页就绪 3s 后采样 2s 实际帧率，<15fps 提示"在浏览器中打开"（localStorage 记住关闭）——任何烂内核环境都能触发，这是环境问题的唯一正解；
> 3. 过程中拔掉的真问题：iframe 衔接预热（双份动画）、光标折射 backdrop-filter: url()、被覆盖仍空转的 rAF——对所有低端安卓机是实打实的性能收益。

## 一、方法论教训

### 1. 先实测，再动手——第一次返工的直接原因

第一轮修复（替换噪点 PNG、canvas 半分辨率、X5 画静态帧）**凭推断直接改代码**，结果：
- 没解决卡顿（真正的负载不在被改的地方）
- 所有移动端都被降级 → 用户骂"所有浏览器都很难看"，全部回退

**教训**：性能问题在无法本地复现目标环境（X5）时，第一动作是**做隔离诊断页让真机说话**，不是改代码。

### 2. 隔离诊断页方法（这次真正定位根因的工具）

在 `public/x5/` 下做了一系列独立页面，每个只包含**一个特性**，全部带 FPS 探针：

```
base（零特效基准）→ canvas（1300粒子）→ noise（feTurbulence）→ blend（巨字混合）
→ canvas-blend（组合）→ scramble（乱码）→ fonts（字体网络）→ hud（每帧DOM写入）
→ quiz-card（毛玻璃）→ full（全组合复刻）→ scroll（纯文本滚动）→ css-anim（纯transform）
→ live（版本检测 + 真实首页帧率）
```

用户在 QQ 里逐个打开报 FPS 数字，凶手一测便知：

| 实测数据 | 结论 |
|---|---|
| base / scramble / hud ≈ 40-60 | 内核基础能力没问题 |
| canvas 粒子"看不到" + full 首页 11fps | Canvas2D 软件绘制，渲染不可见但拖垮主线程 |
| noise 滚动 10fps、quiz-card 滑动 10fps | backdrop-filter / feTurbulence 全走软件 |
| full 答题页 2fps | 三杀手叠加的合成结果 |

**教训**：
- 探针用 rAF 计数每秒帧数，主线程被卡死时它也显示低值——**它测的就是全局帧率**，这正是我们要的。
- "看不到动画"是重要信号：**特效渲染失败 ≠ 无开销**，绘制代码照样在烧 CPU。
- FPS 探针代码要内联（少一个请求），绿/黄/红三档让用户秒懂。

### 3. 用 git 时间线对齐用户的"什么时候开始卡"

用户说"昨天/上周不卡"是最有价值的时间锚点：
```bash
git log --format="%h %ad %s" --date=format:"%m-%d %H:%M" -- <文件>
git diff <不卡的commit>..HEAD -- <文件>   # 只看这之后的改动
```
本次"今天 00:44 的大版本 commit"之后引入的 iframe 衔接预热 + 光标折射就是第一批根因。
**教训**：别怀疑整个代码库，先 diff 用户确认不卡的时间点。

### 4. X5 缓存是幽灵——测试前先证明"测的是新版"

用户多次测试结果矛盾，最后发现 QQ 内置浏览器缓存极其顽固（HTTP `no-cache` 头都拦不住）。
解法：
- 链接带参数：`https://.../?v=xxx` 绕缓存
- 做**版本检测页**（live.html）：fetch 线上 HTML 检查是否含新代码特征字符串，直接显示"✅新版 / ❌旧缓存"
- 给每版部署留一个肉眼可辨的 DOM 标记（如本次首页 HUD 从两行变一行）

**教训**：任何"改了没用"的反馈，先排除"根本没加载到新版本"，再怀疑代码。

## 二、X5 / 老内核技术教训

### 1. 软件路径三杀手（实测数据）

| 特性 | X5 表现 | 处置 |
|---|---|---|
| `backdrop-filter: blur()` | 渲染异常 + 滑动 10fps | `html.x5 * { backdrop-filter: none !important }` 通配覆盖 |
| `feTurbulence`（SVG data-URI 噪点） | **完全不可见**但滚动 10fps | `display:none`（零视觉损失） |
| Canvas2D 逐粒子绘制 | **完全不可见**但 1300 粒子/帧烧 CPU 到 11fps | 不启动 rAF 循环 |
| `mix-blend-mode` | 能渲染，滑动 <20fps | 首页不滚动，静态可接受 → 保留 |

**通用原则**：在低端内核上，"渲染不出来的特效"关掉是纯收益；降级必须 UA 定向，别殃及正常浏览器。

### 2. 帧率掉到几 fps 时，按帧计数的效果会"无限变慢"

TextScramble（乱码解码）按 rAF 帧数推进（每字符 ~40 帧）：
- 60fps → 0.7 秒完成
- 2fps → **20 秒**，用户看到的就是"一个字一个字变、停留很久"

**教训**：基于帧数的动画要设墙钟超时兜底（loader 流程后来加了 2.5s 强制进入），否则低端机上流程卡死。

### 3. 被覆盖 ≠ 被停止

首页隐入背景（iframe 盖上来）后，粒子/光标的 rAF 循环**继续在跑**，白白抢 iframe 的主线程。
修复：进入答题时 `stopHomeAnim()` 停掉首页动画。对所有浏览器都是净收益。

**教训**：视觉上不可见的动画（被覆盖、opacity:0）要主动停 rAF，浏览器不会替你停。

### 4. iframe 预热 = 双份动画同时跑

"衔接预热"（idle 时预载答题页 iframe）在强内核上是体验优化，在 X5 上是灾难：
首页动画 + iframe 内答题页特效同时运行，主线程打满 → "所有页面都卡"（答题页本来就嵌在首页里）。
已回退为点击时按需加载。

**教训**：给低端设备的预算只有"一份动画"。预热/并行加载类优化必须配 UA 降级开关。

## 三、工程流程教训

### 1. `git add -A` 会打包别人的半成品

工作区里有并行会话写入的"文案调配中心"功能（CopyEntry 表 + admin 组件 + API），
`git add -A` 把它们混进"性能修复"commit 直接发布。所幸功能完整、降级优雅，未出事故。

**教训**：commit 前必须逐个看 `git status` 文件清单，确认每个文件都属于本次改动；
不确定来源的文件先单独确认再决定是否带上。

### 2. CI 绿 ≠ 服务器跑的是新代码（Docker Hub 同步延迟）

现象：Actions 全绿，但线上新文件 404、旧内容照旧。
原因：`latest` tag 推到 Docker Hub 后，国内镜像加速器同步有延迟，服务器 `docker compose pull` 拉到的还是旧 digest。

**教训**：部署后要**验证实际产物**（curl 新增文件是否 200 / 内容特征是否出现），
不能只看 CI 状态。同步延迟时 `gh workflow run deploy.yml` 再触发一次即可。

### 3. 404 也会被缓存

发布前探测过的 URL（当时 404），发布后仍 404——CDN 把 404 也缓存了。
验证一律带随机 query 参数；上线新路径前别提前打探测请求。

### 4. public/ 静态文件不做目录索引

Next.js 对 `public/` 只按精确路径匹配：`/x5` ≠ `/x5/index.html`（首页 `/` 能用是因为专门配了 rewrite）。
新增目录页时要在 `next.config.ts` 补 rewrite：
```ts
{ source: "/x5", destination: "/x5/index.html" },
```

### 5. 发布会用本地源码重置 DB 内容——后台改过的数据要先导回

容器 entrypoint 每次启动都跑 `prisma db push + db seed`：
- 批注表被 `deleteMany + createMany` 全量重建（以 `src/lib/annotations.ts` 为权威）
- 题目文案被 `content.yaml → quiz-content.ts` 覆盖

用户在 admin 后台改过的线上数据，**发布前必须先同步回本地源码**，否则被旧版覆盖丢失。
同步路径：公开 `/api/quiz` 可拿题目+角色文案（无需密码）；admin API 需要密码，拿不到的要找用户确认。

### 6. 频繁部署会塞满服务器磁盘（No space on device 事故）

现象：连续十几次部署后，deploy 报 `cp: docker-compose.yml.backup.*: No space left on device`。
根因：每次部署产生一个 compose 备份 + 一个新镜像层，旧的从不清理，磁盘被吃光。
修复（双保险）：
- `scripts/update.sh` 部署最前自清理（compose 备份留 1 份 + image/builder prune）——长期机制；
- `.github/workflows/deploy.yml` 把清理内联进 SSH script——因为服务器从 GitHub raw 拉 update.sh，
  **raw CDN 有约 5 分钟缓存**，刚 push 的修复拉不到（第一版修复因此又失败了一次）。

**教训**：①高频部署的项目，部署脚本必须自带磁盘自清理；②修"部署脚本"本身时，
注意执行路径上有没有 CDN 缓存（raw → 服务器），紧急修复要内联到 workflow 里立即生效。

### 7. 边改边发的大改动要切成可回退的最小单元

本次节奏是：性能修复 → 全回退 → 根因修复 → 又发现混入文件。如果每次都是巨大 commit，
回退会伤及无辜。教训：特效回退 / 功能 / 文案同步分开 commit，回退时才能精准。

## 四、协作教训

1. **降级方案先说清影响范围**：第一次被骂"难看"，根因是把所有移动端都降级了。
   正确姿势：UA 定向（只动 X5）+ "关掉本就看不见的东西 = 零视觉损失"的论证。
2. **给用户可自查的验证手段**：FPS 探针（绿黄红）、版本检测页、肉眼可辨的 DOM 标记——
   让用户回报的数据可量化、可信，而不是"还是卡"。
3. **用户的时间锚点（"上周不卡"）是最好的二分法输入**，追问并 git 对齐它。
