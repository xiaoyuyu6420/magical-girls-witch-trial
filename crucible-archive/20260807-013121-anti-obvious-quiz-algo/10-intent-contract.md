## 已决议的假设（覆盖原 [需澄清]）

- 威胁模型 = 普通用户直觉识破即可；API 收窄为次优，可不作为 P0
- 结果页 = 保留分析，但叙事化包装；不默认展示 userVector/templateVector 技术字符串
- 本轮 = **方案优先**，代码改动等用户确认后再做
- 同答案永远同结果（R8 成立）
- 反向题 = **计分反向**（修 bug），不是仅措辞反向
- 阈值 SPEC vs 代码分歧：方案中给出校准建议，实现时再二选一并写回一致


## BLUF

这次改进只做一件事：让「魔女审判」在**答题过程**和**结果呈现**两个环节都不再把“12 维加权曼哈顿 + 门控触发”这套算法摊在用户面前。

既要挡住普通用户凭直觉看穿（“更狠的选项分更高，结果就是更狠的角色”），也要挡住技术用户用一次 `/api/quiz` + 一次 `/api/match` 就逆出完整评分结构。

**最大歧义是分寸**：为了“看不出算法”，愿意牺牲多少“角色匹配精确感 / 结果可解释性”。结果页现在有雷达图、维度条、`userVector`/`templateVector`、top3 相似度——哪些算沉浸，哪些算泄露，是后续所有设计的分叉点。

## 意图契约（EARS）

### 核心意图

在不动摇“服务端重算、16 人格、门控/触发/兜底”这套既有能力的前提下，消除测试在**答题顺序 / 选项结构 / 结果暴露面**上的“算法可读性”，让用户无法凭直觉或简单请求逆向出计分规则，同时维持结果的可信度与沉浸感。

### A. 答题过程不可识破

- **R1** WHEN 用户连续作答任意 3 道常规题，THE SYSTEM SHALL NOT 让用户能从选项顺序或措辞中稳定推断出“靠后的 / 更激进的选项 = 更高分”。
  - `[假设]` 主要通过“每题选项顺序与分数方向不再恒定一致”达成，而非改变分数本身。
- **R2** WHEN 题目按顺序呈现给用户，THE SYSTEM SHALL NOT 让“前 12 题 = 12 个维度各一题、后接反向校验”这种结构性节奏在题面 / 进度上可被肉眼识别。
  - `[需澄清]` 是打散顺序即可，还是允许加入与计分无关的“叙事 / 氛围题”来打断节奏？
- **R3** WHERE 同一维度有正反两道题，THE SYSTEM SHALL 确保反向题在**计分层**真正反向上分（即反向题的“高分选项”应对应该维度的低档），而非仅在措辞上反向。
  - `[假设]` 当前 `Q()` helper `score: i+1` 导致反向题并未真正反向——这是 bug，应修复。
  - `[需澄清]` SPEC 第 4 节“第 2 题做反向校验（措辞方向与第 1 题相反）”是否指计分反向，还是仅措辞反向？

### B. 结果呈现保留沉浸、不摊开算法

- **R4** WHEN 结果页向用户展示匹配结果，THE SYSTEM SHALL NOT 默认把“12 维向量字符串（userVector/templateVector）、加权距离、档位数值”等算法内部量直接以技术形式呈现给用户。
- **R5** IF 结果页仍要展示维度分析或相似角色对比，THEN THE SYSTEM SHALL 以“叙事化 / 游戏化包装”呈现（如“因子倾向”而非“维度得分”），且不暴露能反推权重 / 阈值 / 距离公式的数值或结构。
  - `[需澄清]` 雷达图、维度条、top3 百分比：保留 / 砍掉 / 包装成什么？
- **R6** WHERE 相似度百分比被展示，THE SYSTEM SHALL 保证它表达的是“契合度 / 共鸣度”等沉浸语义，而非“加权曼哈顿距离换算结果”。
  - `[假设]` 百分比数值本身可保留，但其呈现不应附带可反推公式的周边信息。

### C. 服务端重算不可破坏（防篡改红线）

- **R7** THE SYSTEM SHALL 始终在服务端从 DB 的 option 记录重新计算 `dimScores / gateValue / triggerFired`，前端提交的分数 / 向量 / 结果一律不信任。
- **R8** IF 任何“混淆 / 打乱”手段被引入，THEN THE SYSTEM SHALL 不削弱服务端重算的确定性——同一组 DB option 必须产出同一匹配结果。
  - `[假设]` 混淆只发生在“呈现层 / 出题结构层”，不进入“计分层”。

### D. 既有能力不可破坏

- **R9** THE SYSTEM SHALL 保留 16 种人格（13 常规 + 1 兜底 + 2 特殊）的判定能力，包括门控题触发路径与触发题。
- **R10** WHEN 门控题选触发路径且触发题确认，THE SYSTEM SHALL 仍能正确返回对应特殊人格（相似度 100%）。
- **R11** WHEN Top1/Top2 差距过小且 Top1 偏低，THE SYSTEM SHALL 仍返回兜底人格（UNSET）；差距小但 Top1 足够高时标记“边界型”。
  - `[需澄清]` SPEC 的 `Δ=8% / T=55%` 与代码的 `delta=3 / threshold=40` 哪个为准？

### E. 可维护性 / 可验证

- **R12** WHERE 内容、权重、阈值需要调整，THE SYSTEM SHALL 让这些仍可在 `src/data/quiz-content.ts`（或同等集中位置）独立修改，不需改算法代码。
- **R13** THE SYSTEM SHALL 保留可自动验证的测试（vitest），覆盖：匹配确定性、兜底触发、特殊触发、反向题计分正确性、（新增的）选项顺序与分数方向不再恒定绑定。

### F. 信息暴露面收窄

- **R14** WHEN `/api/quiz` 向前端返回题目与角色数据，THE SYSTEM SHALL NOT 返回能直接还原计分模型的服务端字段（如 `weights`、维度档位映射）给前端，除非该字段是渲染所必需。
  - `[需澄清]` 是否移除 `weights`？`dimensions` 的 dir/model 字段是否算泄露？
- **R15** WHERE 前端需要展示维度，THE SYSTEM SHALL 通过受控的展示字段获取数据，而非在前端 import `parseVector` / `WEIGHTS` 自行解析算法内部结构。

### 非目标

- **NG1** 不改成纯随机 / 纯娱乐结果——匹配仍由算法驱动。
- **NG2** 不放弃服务端重算与防篡改。
- **NG3** 不把项目改造为通用 MBTI / 性格测试平台。
- **NG4** 不重写底层匹配算法（加权曼哈顿 + 门控触发）——本次是“让算法不被看穿”，不是“换算法”。
  - `[假设]` 用户原话指隐藏现有算法，而非替换它。
- **NG5** 不削减 16 人格的内容丰富度（slogan/desc/keywords 不动）。

### 约束

- **C1** 技术栈锁定 Next.js 16 + React 19 + Prisma/SQLite。
- **C2** 匹配算法必须在后端 `/api/match` 执行，前端只展示。
- **C3** 答题明细存 Answer 表，不存 JSON。
- **C4** 进度恢复用 localStorage；若打乱题目顺序，恢复逻辑需兼容。
- **C5** 4 语言（中 / 繁 / 英 / 日）；任何题面 / 包装改动需同步 i18n。

### 成功标准

- **S1** 普通用户做完一次测试，无法仅凭答题过程说出“第 N 题测哪个维度 / 哪个选项分高”。
- **S2** 技术用户仅靠 `GET /api/quiz` + 一次 `POST /api/match`，无法直接读出完整 `WEIGHTS` 表或 `score→tier` 映射。
- **S3** 同一组 DB option，无论选项顺序如何打乱，`/api/match` 返回的 `code` 必须一致。
- **S4** 维度 D 的正反两道题，选“高档语义选项”时合计应把该维度推向高档，而非互相抵消。
- **S5** 结果页默认视图不含 `userVector` / `templateVector` 字符串、不含可反推权重的数值。
- **S6** 特殊人格与兜底人格回归通过。

## 歧义（需确认）

### A1 — 威胁模型
- **读法 A**：只防普通用户直觉识破
- **读法 B**：也防会看 network 的技术用户逆向
- **影响**：是否动 API 契约、是否移除前端算法解析依赖

### A2 — 结果页维度分析
- **读法 A**：完全砍掉雷达图 / 维度条 / 向量字符串
- **读法 B**：保留但叙事化包装
- **读法 C**：维持二级展开，但弹窗内容去技术化
- **影响**：ResultScreen 改动幅度、沉浸感 vs 反泄露

### A3 — 主攻方向
- **读法 A**：以题面 / 选项结构 / 呈现为主，算法核心不动
- **读法 B**：也动匹配层（非线性、交叉项、扰动）
- **影响**：工作量、回归风险、是否违反 NG4

### A4 — 确定性
- **读法 A**：同答案永远同结果
- **读法 B**：允许轻微不可预测
- **影响**：是否引入扰动；与 R8 冲突与否

### A5 — 历史记录
- **读法 A**：兼容现有 TestRecord 解释
- **读法 B**：允许重新解释 / 标注旧版结果
- **影响**：是否需要数据迁移 / 阈值变更策略

## 建议优先澄清的问题

1. 挡到哪一层？普通用户 / 也挡技术用户
2. 结果页维度分析：砍掉 / 叙事化包装 / 维持弹窗但去技术化
3. 是否允许动匹配算法本身？只动出题与呈现 / 也可改匹配层
4. 结果是否严格确定性？同答案永远同结果 / 允许轻微扰动
5. SPEC 与代码阈值分歧以谁为准？SPEC / 代码 / 重新校准
6. 反向题是计分反向还是仅措辞反向？

## 已验证的现状事实（非决策）

1. `/api/quiz` 返回 `dimensions` 与 `weights`
2. `ResultScreen` 前端 import `parseVector`，可渲染 `userVector` / `templateVector` 与 L/M/H/X
3. `Q()` helper 全部 `score: i+1`，注释中的“反向校验”未在计分层真正反向
4. SPEC `Δ=8% / T=55%` 与代码 `delta=3 / threshold=40` 冲突，且单位不同
5. 特殊人格 `SPECIAL_A` 映射依赖 `specialTypes` 顺序
6. 普通题 `/api/quiz` 选项已不返回 `score`（仅 id/label），这是已有的部分防泄露能力

## 推荐默认立场（仅供确认，可改）

若用户不特别反对，建议默认：

- A1 = A+B（普通用户 + 技术用户都挡）
- A2 = B 或 C（保留叙事化分析，不裸露算法量）
- A3 = A（只动出题与呈现，不重写匹配核心）
- A4 = A（严格确定性）
- A5 = A（兼容历史记录；阈值若改，只影响新测试）
- 反向题 = 计分反向（修 bug）
- 阈值分歧 = 重新校准，并写回 SPEC 与代码一致
