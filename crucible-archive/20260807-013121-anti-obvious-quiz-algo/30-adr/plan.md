# 改进方案：让测试不能一眼看出算法

> 范围：方案优先，少改代码
> 威胁模型：普通用户直觉识破
> 约束：严格确定性；反向题计分真正反向；结果页保留但叙事化
> 非目标：不重写匹配核心；不改成随机结果；本阶段不大改实现

## 0. 结论先行

当前最容易“一眼看穿”的不是距离公式本身，而是这三层：

1. **选项结构太直** — 几乎总是 1→2→3，越后面越像高分
2. **反向题没真正反向** — 文案反向，分数仍递增，维度会被对冲/失真
3. **结果页把结构摊开** — 向量字符串、档位、雷达图像“算法报告”

对普通用户，**P0 不需要动加权曼哈顿**。优先改：

- 题面/选项呈现
- 反向题计分
- 结果页叙事包装
- 题序节奏

API 防逆向、非线性匹配、随机扰动 → 本轮不做或降为 P2。

---

## 1. 问题诊断（按“一眼能看出来”排序）

### P0-1 选项顺序与分数方向绑定
- 现象：`Q()` 固定 `score: i+1`，多数题“更狠/更极端”排最后
- 用户直觉：选最右边/最下面 = 某种极端人格
- 证据：`src/data/quiz-content.ts` helper；seed 也 `score ?? j+1`

### P0-2 反向题只是注释，不是计分反向
- SPEC 要求每维第 2 题反向校验
- 实现上仍 1/2/3 递增 → 正反题可能互相抵消或测歪
- 这既是**正确性 bug**，也是体验问题

### P0-3 题序结构感过强
- 前 12 题几乎按 12 维整齐铺开
- 敏感用户会感到“每题测一块不同东西”

### P1-1 结果页算法报告感
- 有雷达图、维度条、top3%、可能暴露向量字符串
- 对普通用户：像心理测量报告，不像“审判书”

### P1-2 阈值 SPEC/代码不一致
- SPEC：`Δ=8%`, `T=55%`
- 代码：`delta=3`, `threshold=40`
- 单位与数值都不同 → 兜底频率与“边界型”不可预期

### P2（本轮不优先）
- `/api/quiz` 返回 `weights`（技术用户才关心）
- 前端 `parseVector`
- `SPECIAL_A` 依赖 specialTypes 顺序（稳定性问题，非“一眼看穿”）
- 引入非线性/扰动（违反“先少改 + 严格确定”）

---

## 2. 目标体验（确认后的产品口径）

| 场景 | 用户应感觉到 | 用户不应感觉到 |
|------|--------------|----------------|
| 答题 | 在监牢里做道德/命运抉择 | “这题在测信任度，C 分最高” |
| 反向题 | 换角度被追问 | 同一维度被重复问且选项梯度相同 |
| 结果 | 被判定为某角色 + 灵魂倾向解读 | 12 维向量 / L M H X 技术档 / 距离公式感 |
| 再测 | 同答案同结果，可信 | 随机抽角色 |

---

## 3. 方案总览（推荐组合：A 呈现混淆 + B 计分修正 + C 结果叙事）

```
[题库层]  选项顺序打散 + 反向题真正反分 + 题序重排
   │
[匹配层]  核心算法不动；仅修反向分与阈值文档一致性
   │
[结果层]  保留分析，改成“因子/灵魂”叙事，隐藏技术向量
   │
[测试层]  补 vitest：反分、顺序无关、确定性、特殊/兜底回归
```

**不采用**：结果随机扰动、重写距离函数、本轮大改 API 契约。

---

## 4. 分项方案

### 4.1 选项顺序打散（对普通用户收益最大）

**做法**
- 内容层为每题定义稳定的 `score`（语义正确）
- 展示层对选项做**稳定打乱**（按 `questionId` 派生种子，同题永远同序）
- 用户看到的 A/B/C 不再等于 1/2/3

**为什么用稳定打乱**
- 满足严格确定性
- 进度恢复 / 键盘 1/2/3 仍可用
- 不依赖 session 随机

**实现落点（确认后再做）**
- `quiz-content.ts` 或 seed：显式写 score，不再依赖数组下标
- `TestScreen` 或 `/api/quiz`：返回前按题打乱 options（只打乱顺序，id 不变）
- 服务端匹配仍只信 `optionId`

**验收**
- 任意连续 3 题，无法从“选项位置”猜高低分
- 同 `optionId` 集合 → 同结果

### 4.2 反向题真正反分（正确性 + 反识破）

**定义（锁定）**
对维度 D：
- 正向题：语义“高 D” → 高 score
- 反向题：语义“高 D” → 仍应推高 D 的档位

注意：不是“选项数组反过来”，而是**语义对齐后的计分映射**。

**推荐落地**
1. 审计 12 个维度的第 2 题，标出“哪句是高档语义”
2. 给反向题显式 `score`（例如 3,2,1 或按语义重排），不要 `i+1`
3. 增加 vitest：同一维度两题都选“高语义” → tier 应偏 H/X，不应互相抵消

**示例（B1 信任度）**
- 正向：愿意信任 → 高分
- 反向题若选项从“警惕”到“全盘托出”，则“全盘托出”仍应高分；若文案顺序是警惕在前，则 score 可能是 1,2,3 或打乱后仍绑定 label

### 4.3 题序重排（降低结构感）

**现状**
- 前 12：S1 F1 B1 W1 … 整齐
- 中段：部分反向 + gate/trigger
- 后段：剩余反向

**推荐**
- 保持 24 常规 + 1 gate + 1 trigger 总量
- 用**交错维度**，避免连续暴露“一维一题”
- gate 仍放中后段（叙事高潮），trigger 仍条件显示
- `order` 字段调整即可，算法不依赖题序

**可选加强（P1）**
- 不加假题也行；若要更沉浸，可加 1–2 道**不计分氛围题**（需 DB type 或 score=0 约定）— 本轮标为可选，因会动数据模型/i18n

### 4.4 结果页叙事化（保留分析，去报告感）

在“只挡普通用户”前提下，**不必**先拆 API；先改文案与默认展示。

| 现在 | 改成 |
|------|------|
| 维度分析 / L M H X | 因子倾向 / 低语·共鸣·侵蚀 等叙事档 |
| userVector 字符串 | 默认不展示；需要时仅内部/admin |
| templateVector | 不展示 |
| 雷达图 | 保留，标题改为「灵魂图谱 / 因子共鸣」 |
| 维度条 | 保留，标签用角色世界观用语 |
| top3 % | 保留为「相近的命运 / 共鸣者」 |
| similarity % | 保留为「契合度 / 审判契合」 |

**文案原则**
- 不出现：向量、权重、曼哈顿、档位码、distance
- 可以出现：因子、审判、侵蚀、羁绊、觉醒、共鸣

**实现落点**
- `ResultScreen.tsx` + i18n 四语
- 详细分析弹窗同样去技术化
- 分享图跟随叙事文案

### 4.5 阈值校准（方案建议，实现时二选一）

| 方案 | 含义 | 建议 |
|------|------|------|
| 跟代码 | delta=3, threshold=40 | 改动小；更新 SPEC 说明单位是“相似度百分点差” |
| 跟 SPEC | Δ=8%, T=55% | 兜底更严/更松需回放数据验证 |
| 重校准 | 用现有 TestRecord 分布仿真 | 最稳，但要分析数据 |

**推荐**：先**以代码为准写回 SPEC**（低风险），另开一条“用真实分布重校准”的后续任务。  
本轮目标是反识破，不是重做边界人格产品定义。

### 4.6 特殊人格映射稳定性（顺手 P2）

- `SPECIAL_A` → 显式 map 到 `YUKI`/`ETL`，不依赖 DB 顺序
- 与“一眼看穿”弱相关，但便宜，可在动 `match.ts` 时顺手做

## 8. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 改反向分导致人格分布漂移 | 先在本地用 seed 全组合/蒙特卡洛看 top 人格分布；保留变更说明 |
| 打乱选项导致“1/2/3 键”与视觉顺序混淆 | 键位绑定**当前渲染顺序**，不是 score |
| 叙事化后用户觉得结果“更玄、更不准” | 保留契合度与 top3 共鸣，只去掉技术词 |
| 历史 TestRecord 用旧分解释 | 只保证新测试；后台可标注算法版本（可选字段，非本轮必须） |

## 9. 成功标准（对普通用户）

1. 不能靠“总选最后一项”稳定刷到某一类极端角色（因顺序已打散 + 反分）
2. 做题时感觉是剧情抉择，不是量表
3. 结果像审判书/命运揭示，不像心理测量报表
4. 同答案 → 同角色（严格确定）
5. 特殊/兜底/门控路径不回归

## 11. 新增目标：题库模板化 / Content Pack（可套用到别的题目）

> 用户补充：希望把题目拆成模板，之后这个项目可以套用到别的题目上。

### 11.1 现状：已经半模板，但还不是引擎

**已经像模板的部分**
- 题目 / 选项 / 人格在 DB（`Question` `Option` `PersonalityType`）
- 后台可编辑 + Excel 导入导出（`/api/admin/template` `/api/admin/import`）
- 匹配吃的是 `dimScores + types[]`，不完全绑死角色名
- 前端答题主要吃 `questionId/optionId`

**还绑死「魔女审判」的部分**
| 层 | 硬编码 | 影响 |
|----|--------|------|
| 维度模型 | `DIMENSIONS` / `WEIGHTS` / `ALGO_CONFIG` 在 `quiz-content.ts` | 换主题仍是 S/F/B/W 12 维 |
| 匹配规则 | gate 值 `destroy/endure/normal/normal_alt`；特殊触发 `SPECIAL_*` | 别的主题语义对不上 |
| 结果 UI | `MODEL_GROUPS`、维度名、审判文案 | 换题也像魔女测试 |
| i18n / 落地页 | 大量魔女文案、`witch-trial-*` storage key | 主题泄漏 |
| Schema | 没有 `QuizPack` / `Dimension` 表 | 维度不能随题包变 |
| Seed | 单包 seed | 不能 `load pack X` |

结论：现在是 **「单主题 CMS」**，不是 **「多主题测验引擎」**。  
模板化的正确目标是：

> **一套引擎 + 多个 Content Pack**；换题 = 换包，不改匹配核心代码。

### 11.2 目标形态

```
┌─────────────────────────────────────────────┐
│  Engine（稳定，少改）                          │
│  match / answer-processor / test flow        │
│  admin shell / rate-limit / results          │
└─────────────────┬───────────────────────────┘
                  │ load
┌─────────────────▼───────────────────────────┐
│  Content Pack（可替换）                       │
│  pack.json + dimensions + questions + types  │
│  + copy/i18n + theme tokens + rules          │
└─────────────────────────────────────────────┘
```

一个 Pack 至少描述：
1. **元信息**：id、name、version、locale 默认值
2. **维度**：code、name、group、weight、展示文案
3. **算法参数**：tiers、delta、threshold（可覆盖默认）
4. **题目**：order、type、dim、options(score/value/trigger)、translations
5. **结果类型**：code、vector、group、special、文案
6. **规则**：gate 枚举、trigger 映射、normal 微调映射（可选）
7. **呈现**：结果页标签、进度文案、主题色（可选）

### 11.3 推荐分层（避免一次做成平台）

#### L1 — 内容文件模板（最小可用，推荐先做）
把「可替换内容」从代码常量抽成 **一个 pack 目录/文件**：

```
content/packs/witch-trial/
  pack.json          # id, title, algo, gateRules
  dimensions.json    # 12 dims + weights
  questions.json     # 26 题
  types.json         # 16 人格
  copy/zh-CN.json    # UI 文案（可选先继续用 src/i18n）
```

- seed / import 从 pack 读
- `match.ts` 不再 import 魔女专用 `DIMENSIONS`，改为运行时注入 `PackConfig`
- 仍可 **单 active pack**（env: `ACTIVE_PACK=witch-trial`）

**收益**：换题时主要改 pack，不改引擎。  
**成本**：中等；不动多租户。

#### L2 — DB 完整内容包（后台可换包）
新增：
- `QuizPack`（id, slug, version, active）
- `Dimension`（packId, code, name, weight, group…）
- Question/Type 增加 `packId`

Admin：选择 active pack / 导入整包 Excel（多 sheet：Pack / Dims / Questions / Types）

**收益**：运营可热切换。  
**成本**：迁移 + admin 大改。

#### L3 — 真正多主题产品
多 landing、多路由 `/p/[pack]`、多套视觉、分享卡模板……  
**本阶段不建议**，等 L1/L2 跑通。

### 11.4 与「反一眼看穿」如何叠加

模板化不仅是换题，还能把反识破做成 **pack 级能力**：

| 能力 | 放在 Engine | 放在 Pack |
|------|-------------|-----------|
| 选项稳定打乱 | 引擎默认开启 | pack 可关 |
| 反向题 score 显式 | 引擎校验 | pack 数据负责写对 |
| 结果叙事标签 | 引擎用通用槽位 | pack 提供文案 |
| 维度数 / 权重 | 引擎泛化 N 维 | pack 定义 |
| gate/trigger | 引擎执行通用规则表 | pack 定义映射 |

这样以后换「职场人格」「动漫角色」「产品选型」题包，也能自带：
- 不按 1/2/3 排高分
- 结果不露向量字符串
- 严格确定性

### 11.5 最小 Pack Schema（草案）

```json
{
  "id": "witch-trial",
  "version": 1,
  "title": "魔女审判",
  "algo": {
    "tiers": [{"max": 2, "value": 0}, {"max": 4, "value": 1}, {"max": 5, "value": 2}, {"max": 6, "value": 3}],
    "delta": 3,
    "threshold": 40,
    "vectorFormat": "groups-of-3"
  },
  "dimensions": [
    {"code": "S1", "name": "严厉度", "group": "S", "weight": 1.5}
  ],
  "rules": {
    "gateValues": ["destroy", "endure", "normal", "normal_alt"],
    "gateBonus": {"normal": {"S2": 1}, "normal_alt": {"W1": 1}},
    "specialTriggers": {"SPECIAL_A": {"destroy": "YUKI", "endure": "ETL"}},
    "optionShuffle": "stable-by-question-id"
  },
  "questions": [/* ... */],
  "types": [/* ... */],
  "presentation": {
    "result": {
      "fitLabel": "审判契合",
      "analysisLabel": "因子倾向",
      "topLabel": "相近的命运"
    }
  }
}
```

引擎契约：
- `processAnswers(answers, options, pack.rules)`
- `match(input, types, pack.algo + pack.dimensions + pack.rules)`
- UI 读 `pack.presentation` + i18n

### 11.6 迁移路径（与现有反识破 Slice 对齐）

**不建议**一上来做多 pack 路由。建议：

1. **Slice 0.5 / 与 Slice 1 并行设计**  
   定义 pack schema + 把 `quiz-content.ts` 视为 `witch-trial` 的第一包（可先仍是 TS 模块）
2. **Slice 1（反识破）在 pack 数据上做**  
   反分、打乱、叙事文案都写进 pack，而不是写死组件
3. **Slice T1 — 抽引擎接口**  
   `match`/` Rel` 去硬编码维度常量；单测用 fixture pack
4. **Slice T2 — seed/import 吃 pack**  
   Excel 增加 Dimensions sheet；Questions/Types 保持
5. **Slice T3（可选）— DB QuizPack**  
   真·可切换

### 11.7 换题时你真正要准备的「模板清单」

给未来任意主题一份填空表：

1. 维度表（N 维，建议仍 8–12）  
2. 权重  
3. 每维 ≥2 题（含反向语义 + **显式 score**）  
4. 结果类型（向量两两可区分）  
5. 可选：gate / trigger / fallback  
6. 文案包（欢迎/答题/结果/分享）  
7. 展示规则（是否打乱、分析用词）  
8. 视觉 token（可选）

### 11.8 风险

| 风险 | 说明 | 缓解 |
|------|------|------|
| 过度平台化 | 一次做多租户烧预算 | 先 L1 单 active pack |
| 维度数可变 | UI 雷达图/分组假设 12 维 4 组 | 引擎按 `dimensions[]` 动态渲染 |
| 向量格式 | 现格式 `LLL-MMM-...` 假设 4×3 | pack 声明 groups；或改存 number[] JSON |
| i18n 双源 | DB translations + src/i18n 角色文案 | 新 pack 以 DB/pack 为准，UI 槽位通用 key |
| 历史记录 | 换包后旧 resultCode 难解释 | record 记 `packId+version` |
